# 找工 Agent 網站：從經驗整理到 Offer 的完整工作台

狀態：需求與設計規格，尚未實作網站。適用市場：台灣與美國／國際。

網站涵蓋所有既定功能：建立完整經驗資料庫、從同一份資料生成多種履歷、搜尋台灣與國際職缺、針對職缺客製履歷、自動投遞、面試與面經，以及 offer／最終結果。所有日常操作都從網站發起並在網站查看結果，使用者無須編輯 JSON、操作命令列或另外呼叫 Agent。

完整流程：輸入文字／語音經驗 → 整理並更新經驗資料庫 → 生成多版履歷 → 搜尋與配對職缺 → 依職缺客製履歷 → 投遞 → 面試與面經 → Offer／最終結果。經驗、履歷、職缺和申請共用資料關係；同一家公司的不同職位各自有申請紀錄。

## 我的經驗：輸入、整理、持續更新

輸入區支援直接貼一大段經驗、錄音與音檔上傳，也能匯入舊履歷。錄音具備開始、停止、預覽、刪除及上傳操作；使用者拒絕麥克風權限時仍可打字或上傳音檔。錄音和逐字稿可以一起查看，修正逐字稿不覆蓋原始素材。

「整理我的經驗」會把素材整理成工作、專案、技能、學歷、成果與求職偏好。畫面標示待補資訊，透過對話補充責任範圍、時間和成果；使用者可編輯、合併重複項目，保留每段內容對應的原文。未知成果數字留白，不自行估算。

個人資料庫同時提供分類編輯和完整 Markdown 文件預覽／下載。新增素材以差異方式呈現；遇到日期或數字衝突，讓使用者選擇正確內容。確認更新後，新生成的履歷使用新資料；舊履歷和歷史投遞仍保留原版本。刪除已被引用的經驗時保留歷史快照，並在下一次生成時排除。

## 履歷工作室：一份經驗、多個方向

使用者在網站選擇一個或多個目標職位、繁中／英文、版型和篇幅，按下生成後得到可獨立編輯的多份履歷。職位方向由使用者指定或根據已提供經驗提出建議，不預設每個人都具備後端、AI 或全端能力。

編輯畫面包含段落編輯、履歷預覽與經驗依據；可調整段落順序、移除項目、儲存新版本、比較修改、回到舊版本或匯出 PDF／DOCX。每次回到舊內容亦建立新版本，不覆蓋既有投遞紀錄。

使用者可從職缺頁直接按「產生此職缺履歷」，或在履歷工作室選取職缺。網站顯示職缺要求、可使用的經驗、修改前後差異與仍缺少的條件。只調整有依據的選材、排序與表達；缺乏的技能列為缺口。修改內容不自動寫回個人經驗。

生成期間顯示進度、失敗原因及重試方式。未完成生成、驗證失敗或匯出失敗的項目明確標示；不提供空白檔案假裝完成，也不讓未通過事實檢查的版本進入自動投遞。

## 找職缺：搜尋、篩選、配對、客製

網站提供搜尋條件表單，支援台灣與美國／國際、職位關鍵字、城市、遠端偏好、薪資幣別與期間、工作許可／簽證需求，以及排除公司。使用者可以保存條件並再次啟動搜尋，也能貼上網址或職缺描述。每個來源顯示當前支援程度與最近更新時間。

搜尋結果顯示公司、職位、地點、來源、原文連結、薪資（有提供時）、條件匹配原因與缺口。將硬性不符合、未知及偏好差異分開，不把缺少工作許可資訊當成已符合。跨平台的同一職缺去重，保留各來源連結。

職缺詳情可查看原始描述與整理後要求，並直接收藏、排除、產生客製履歷或加入投遞佇列。履歷生成完成後回到該職缺／申請，不要求使用者手動下載再上傳到另一個模組。篩選或搜尋失敗要呈現真實狀態；沒有結果和來源暫時不可用分開。

## 投遞中心：從網站啟動和管理 Agent

網站提供草稿、批次投遞與規則自動投遞模式，保留既定的公司排除、職位／國家條件與每日上限。使用者可選定職缺與文件批次執行，或啟動已設定的自動規則，不必逐筆重新核准相同範圍。

佇列顯示準備履歷、填寫申請、等待資料、送出中、已送出、失敗或結果待查。必要問題在網站補答後回存情境相符的答案庫，繼續原任務。需要登入或操作驗證碼時，提供對應申請頁與接手方式，完成後回報並續跑。

使用者可暫停後續佇列、取消尚未送出的任務，以及重試可確認未送出的失敗項目。已送出的申請不能透過取消按鈕變成未投遞；送出狀態不明先查證，避免重投。佇列、任務和進度儲存在後端，重新開啟網站可接續查看。

## 各頁面的共用任務體驗

經驗整理、音檔轉錄、履歷生成、職缺搜尋、文件匯出和投遞均由網站發起，具備準備中、執行中、待使用者處理、完成與失敗狀態。任務綁定發起時的經驗／履歷／條件版本。執行期間若使用者修改資料，完成結果仍標明所用版本，並提供以最新資料重跑的操作。

模組之間用同一筆資料連接，不要求使用者反覆填入已提供的資料；跨頁仍保留任務進度。前端的功能完成標準是能呼叫實際後端並持久保存結果，只有按鈕或固定範例畫面不能算功能完成。

## 自動記錄的來源

| 發生的事情 | 系統如何更新 | 尚未接通來源時 |
| --- | --- | --- |
| Agent 準備申請 | 建立準備中的紀錄，綁定職缺、履歷版本與答案 | 可手動建立申請 |
| Agent 完成送出 | 收到可核對的成功證據後，記錄已投遞、時間和附件版本 | 不把僅開啟網頁或上傳履歷視為已投遞 |
| 收到面試邀請 | 從使用者連接的信箱／招募系統回覆中辨識，連到原申請 | 使用者手動新增邀請或貼上通知 |
| 面試改期／取消 | 更新該輪面試，保存原時間與變更事件 | 使用者可手動修改 |
| 收到 offer／拒絕 | 依明確通知更新，保留來源 | 使用者補登結果及可選附件 |
| 使用者在別處自行投遞 | 透過手動新增或已接通且可驗證的回覆補登 | 不宣稱能自動看到所有站外活動 |

網站本身不能憑空得知是否得到面試或 offer；完整自動化需要 Agent 事件和回覆來源。第一版將手動補登與自動同步寫入同一套資料模型。網站顯示「Agent 記錄／信箱同步／使用者更新」及最近同步時間，未連接時明確顯示尚未同步。

信件分類的「收到訊息」和「實際事件」分開：面試提醒不是新面試，一般自動收件通知不是面試邀請，薪資討論不是正式 offer。無法判斷職缺歸屬或有相互矛盾的資料時，進待確認清單。使用者更正不被較舊的同步事件覆蓋。信箱同步以讀取及辨識為範圍，不代替使用者寄信、回覆或接受 offer。

## 申請進度和事件

看板主線：準備中 → 已投遞 → 面試中 → Offer → 已接受。

另有待補資料、送出結果待查、已拒絕、已撤回、offer 已婉拒、offer 已失效等狀態。長時間沒回覆顯示「尚未回覆」，不自動當成拒絕。可以有多輪面試，也可以沒有面試就直接收到 offer。

面試邀請、排定時間、完成面試、下一輪邀請分開記錄；一筆申請可以包含多個 interview。每次狀態變動保留來源、事件時間、記錄時間、前後狀態與更正歷史。最終未拿到 offer 要區分拒絕、主動撤回或流程未結束。

Agent 對接以持久化事件為基礎，初步事件類型包括 application.prepared、application.submitted、application.submission_unknown、interview.invited、interview.updated、application.rejected、offer.received 和 offer.updated。所有事件具備穩定事件 ID；伺服器驗證事件所屬使用者、申請與證據。網路重試不重複建立投遞或面試。

## 履歷版本

每次投遞綁定不可被後續修改覆蓋的文件快照，包含文件雜湊、語言、版本、建立日期、職缺與使用的經驗來源。使用者改履歷時建立新版本，歷史申請仍能下載當時那一份。

若平台使用站內履歷，另記錄站內履歷內容或可取得的快照，不假設每次投遞都能上傳不同 PDF。不同履歷版本的面試／offer 統計只描述已發生的結果，不把觀察上的差異直接解釋成履歷造成的效果。

## 面經上傳

第一版支援直接輸入文字，以及 TXT、Markdown、PDF 檔案上傳；可依後續需求擴充錄音和截圖。必須能在申請或面試輪次下上傳，亦可先存未分類筆記，之後指定歸屬。

面經欄位：公司、職位、面試輪次、日期、面試形式、題目、自己的回答、回饋、待補強項目與下一步。非必填欄位允許留空；主觀感受與面試官明確回饋分開。

AI 整理面經時保留原檔與原文，輸出可修改的摘要、題目分類與複習清單；沒有記錄的題目或評語不補寫。解析失敗時仍保留可下載的原檔，清楚顯示失敗並可重試。上傳完成和 AI 整理完成是不同狀態。

面經預設只有本人可見。使用者此次要求的是上傳與管理，公開分享、匿名社群或跨使用者搜尋不列入第一版。

## Offer 資料

每筆申請可有 offer 及其條件修訂紀錄。欄位包括收到日期、正式／待正式文件、職位、地點、幣別、底薪及其月／年期間、可選獎金和股權、回覆期限、預計到職日、備註及附件。

「收到 offer」與「接受 offer」是不同事件。更新條件不能重複累加 offer 數。台幣月薪和美元年薪保留原單位，不直接混加。是否接受、婉拒由使用者記錄，不因系統推測而自動回覆公司。

## 統計定義

- 已投遞數：有確認送出或使用者明確補登的獨立申請數；草稿、失敗和送出結果待查不計入。
- 獲邀面試數：至少一次明確面試邀請的申請數；同職缺三輪面試算一筆，輪次另計。
- 收到 offer 數：至少收到一份明確 offer 的申請數；修訂條件不重複計數。
- 面試邀請率：同一投遞日期範圍中，已獲邀的申請數／已投遞申請數。
- Offer 率：同一投遞日期範圍中，已收到 offer 的申請數／已投遞申請數。

分母為零顯示尚無資料。篩選期間依投遞日期形成同一批申請，數字標示截至目前，避免把本月面試除以本月新投遞造成誤導。重開瀏覽器或換裝置後，同一帳戶應得到相同資料。

## 前後端分工與資料歸屬

前端負責查看、篩選、編輯、上傳和狀態呈現；後端負責帳戶、持久化記錄、附件存取、狀態變更與事件驗證；Agent 負責實際搜尋、履歷生成及申請操作。後端收到事件後，前端透過訂閱或輪詢刷新進度，不讓瀏覽器頁面是否開啟決定任務是否繼續。

資料實體：user、source_material、transcript、career_fact、career_revision、resume_version、search_preferences、search_run、job_snapshot、application、application_event、agent_task、answer_bank、interview、interview_note、attachment、offer、integration_connection。每項私人資料綁定使用者，下載附件和查詢詳細紀錄都在後端驗證歸屬。自動化憑證只能更新對應使用者範圍。網站不把履歷、面經和 offer 附件放在公開檔案網址。

## 第一版驗收

1. 使用者可完全透過網站完成：文字／語音輸入經驗 → 整理及編輯經驗資料庫 → 匯出 Markdown → 生成兩種方向及中英文履歷 → 搜尋台灣／國際職缺 → 依職缺客製 → 發起投遞 → 兩輪面試 → 上傳面經 → 收到 offer → 記錄最終決定。搜尋與投遞需依真實接入來源驗證，不用固定樣本代替。
2. 同一家公司的兩個職位、同一職缺的多輪面試，都不會被合併錯誤。
3. Agent 成功事件會自動出現在網站；同一事件重送三次只有一筆紀錄。沒有成功證據時顯示待查，不假裝投遞完成。
4. 更新基礎履歷不會改變過去投遞的文件；每筆申請能取回當次履歷。
5. 面經可上傳、查看、修改整理稿及下載原檔；上傳失敗與解析失敗能區別。
6. 面試邀請和 offer 的自動辨識在接通真實來源後驗證；未接通時介面如實顯示可用的手動方式。
7. 統計依上述定義計算；三輪面試和 offer 條件修訂不會灌高數字。
8. 兩個帳戶互相不能讀取、修改或下載對方資料；重新登入後紀錄和附件仍存在。
9. 手機可更新進度和上傳面經；桌面可篩選並查看完整申請時間軸。
10. 音檔轉錄、經驗整理、履歷生成均有真實進度與失敗處理；錄音權限被拒絕時，文字和上傳仍可用。
11. 同一份經驗資料生成的不同履歷可分別預覽、修改、比較和匯出；新增經驗後可用最新資料重新生成，不改掉歷史申請。
12. 使用者能在前端保存求職條件、啟動搜尋、查看匹配依據、從職缺直接生成專用履歷並加入投遞。
13. 草稿、批次和規則模式均能從前端設定及啟動；暫停、補答、續跑和可安全重試的失敗項目均有操作入口。
14. 使用者離開再返回網站能看到任務真實狀態；不同模組共用經驗、履歷和申請紀錄，不要求重複輸入。

實作順序依完整使用流程推進：先建立網站共用架構與經驗資料庫，再完成履歷工作室、職缺搜尋和客製化，接上投遞中心，最後貫通面試、面經及 offer。每一階段一起完成前端入口、後端操作和資料保存；上述全部模組都是已確定的交付範圍。分階段開發不代表將經驗整理、履歷生成或搜尋／自動投遞排除在網站之外。
