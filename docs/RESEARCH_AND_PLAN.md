# 找工 Agent：GitHub 研究與第一版規格

研究日期：2026-09-18（美西）。本次完成公開文件與部分核心程式碼檢視，尚未安裝或實測投遞成功率。目標市場已確認：台灣與美國／國際。使用者已確認所有功能都要在前端網站操作，包括完整經驗資料庫、多版履歷生成、職缺搜尋與客製、自動投遞、面試、面經與 offer；完整網站規格見 [WEB_PRODUCT_SPEC.md](WEB_PRODUCT_SPEC.md)。目標職位尚待提供。

建議建立自己的「職涯資料庫＋履歷生成」核心，參考 ApplyPilot 的搜尋與投遞流程。先以受控的小批次實測決定是否沿用它的執行引擎；履歷事實驗證需要重新設計。

## 參考專案與取捨

| 專案 | 查到的功能 | 適合參考的部分 |
| --- | --- | --- |
| [Pickle-Pixel/ApplyPilot](https://github.com/Pickle-Pixel/ApplyPilot) | 搜尋、補齊職缺、評分、客製履歷、求職信、瀏覽器投遞；AGPL-3.0 | 整體流程、分階段重跑、搜尋與投遞模組 |
| [ibarrajo/ApplyPilot](https://github.com/ibarrajo/ApplyPilot) | 原版 fork，另有人工接手、問答庫、登入狀態保存、Gmail 回覆追蹤 | 未知問題只問一次、失敗恢復、追蹤投遞結果；目前僅檢視文件 |
| [Fearplay/applypilot-ai](https://github.com/Fearplay/applypilot-ai) | 以職缺與履歷等資料產出客製文件、補充問題、證據報告；README 標示 MIT | 經驗來源追溯、文件編輯與匯出；目前僅檢視文件 |

原版 ApplyPilot 是 Python CLI，完整投遞依賴 Claude Code、Chrome 與 Playwright MCP；選用其他文字生成模型，不代表投遞執行器也已替換。依據：[README](https://github.com/Pickle-Pixel/ApplyPilot)、[套件設定](https://github.com/Pickle-Pixel/ApplyPilot/blob/main/pyproject.toml)、[投遞啟動器](https://github.com/Pickle-Pixel/ApplyPilot/blob/main/src/applypilot/apply/launcher.py)。

讀取原版 [tailor.py](https://github.com/Pickle-Pixel/ApplyPilot/blob/main/src/applypilot/scoring/tailor.py) 後，有兩項必須修正：生成提示允許加入少數相近技能；品質判定提示容許小幅延伸，而且最後一次重試即使判定失敗，仍可能產生 approved_with_judge_warning 並被後續視為成功。這不符合「履歷只根據我提供的經驗」的需求。

原版 [profile 範例](https://github.com/Pickle-Pixel/ApplyPilot/blob/main/profile.example.json) 把工作許可、薪資等放在共用欄位。雙市場版本應分國家保存工作許可、簽證需求、薪資幣別與期間，未知值保留空缺，不能沿用範例的 Yes／No。登入憑證另存，不放進職涯文件或模型提示。

## 使用流程

1. 使用者貼上零散經驗、透過系統語音輸入，或上傳錄音。錄音先轉成逐字稿，保留時間戳與原文。
2. Agent 整理出工作、專案、技能、學歷、成就和求職偏好；只對缺少且會影響履歷的資訊追問。
3. 產出可閱讀的 career.md，以及可供程式處理的結構化資料。使用者可以持續補充，不需要先寫好履歷。
4. 依目標職位生成數份基礎履歷，例如後端／AI／全端；這些只是示例，不預設使用者具備相關背景。
5. 搜尋台灣與國際職缺，去重、檢查硬性條件，列出適合原因、缺口與待確認事項。
6. 對每個職缺挑選真實經驗、調整措辭與排序，產出中／英文履歷、求職信與問答草稿。
7. 依使用者設定的投遞模式自動填寫或送出，保存當次文件版本、填答內容、時間與送出證據。
8. 網站自動接收投遞事件；每筆申請能查看履歷快照、面試輪次、上傳面經及最終結果。接通信箱或其他有效回覆來源後，自動更新有證據的面試與 offer 狀態，並允許使用者補登與更正。

這裡的 fine-tune 是「依職缺客製履歷」。第一版使用現成模型與經驗檢索即可，不需要訓練專屬模型；資料量小時也不必先建向量資料庫。

## 資料設計

| 資料 | 內容與用途 |
| --- | --- |
| 原始素材 | 文字、錄音、逐字稿、舊履歷，保留來源，不被生成結果覆蓋 |
| career.json | 結構化職涯事實的主資料，包含穩定 ID、來源段落、日期、角色、技能、成果、確認狀態 |
| career.md | 由主資料生成的可讀文件；修改後匯入時先顯示差異，避免兩份資料各自變動 |
| preferences.json | 目標職位、國家／城市、遠端、薪資幣別與期間、排除公司、各國工作許可 |
| answer_bank | 常見申請問題與使用者答案，標示適用國家／情境、更新日期 |
| job_snapshot | 職缺 ID、原始網址、公司、描述、條件、抓取時間；內容更新後保留版本 |
| resume_version | 基礎／職缺專用版本、語言、使用的事實 ID、修改差異、PDF／DOCX 路徑 |
| application | 職缺與履歷版本、當次答案、狀態、送出證據、錯誤與重試紀錄 |
| application_event | 每次狀態變動、資料來源、事件時間、佐證與去重鍵 |
| interview / interview_note | 各輪面試時間、進度、題目與心得、上傳原檔及整理版本 |
| offer | offer 收到日期、幣別與薪資期間、條件、回覆期限、接受／婉拒／失效等結果 |

每條生成敘述都要附來源，並檢查來源是否真正支持該敘述。技能、任職公司、職稱、日期與數字另做結構化比對；不能只因為存在來源 ID 就判定通過。職缺要求的技能若沒有經驗證據，列為缺口，不能寫成已具備。改寫後的履歷也不能自動回寫成新的職涯事實。

## 台灣與國際來源

搜尋與投遞要分開標示支援程度，例如「可匯入」「可搜尋」「可填表」「可確認送出」，逐站驗證。

| 範圍 | 第一版策略 | 尚待驗證 |
| --- | --- | --- |
| 國際企業官網、Greenhouse／Lever | 先從指定公司公開職缺取得資料，申請時進實際表單 | 各公司自訂問題、附件與成功確認流程 |
| Workday | 評估 ApplyPilot 既有搜尋與瀏覽器流程 | 登入、多頁表單與網站差異 |
| Indeed 等聚合來源 | 評估 ApplyPilot／JobSpy 搜尋模組；追蹤實際申請網址 | 目前可用率、地區覆蓋、重複職缺 |
| 台灣 104、Cake、Yourator | 列入獨立 connector 工作清單；先支援網址／描述匯入，再逐站完成搜尋與投遞 | 是否有適用存取方式、登入後履歷格式、是否支援每職缺不同附件 |

[JobSpy 文件](https://github.com/speedyapply/JobSpy/blob/main/README.md) 列出 Indeed 可搜尋 Taiwan；這不等於支援 104、Cake 或 Yourator。原版 ApplyPilot 文件也沒有列出這三個台灣平台的專用 connector。

Greenhouse 公開 GET 可取得職缺，但申請 POST 需要 Job Board API key；Lever 的申請 POST 同樣需要帳戶管理員產生的 key。因此不能把「公開職缺 API」當成求職者通用的投遞 API。依據：[Greenhouse 官方文件](https://docs.greenhouse.io/job-board.html#authentication)、[Lever 官方文件](https://github.com/lever/postings-api#creating-applications)。

台灣來源參考：[104 職缺搜尋](https://www.104.com.tw/jobs/search/)、[Cake 職缺](https://www.cake.me/jobs?locale=zh-TW)、[Yourator](https://www.yourator.co/)。這些是接入候選，尚未驗證自動投遞。

## 投遞模式與完成判定

- 草稿模式：自動準備履歷、填答及申請頁，供檢查。
- 批次投遞：使用者選取職缺與對應履歷後，依選定內容送出。
- 規則自動投遞：使用者設定國家、職位、公司排除清單、必備條件、每日上限及預算，符合規則就自動送出，無須每筆重問。

未知的工作許可、薪資或必要問題移入待補資料；已有答案且情境相符時直接重用。登入、驗證碼或無法判讀的表單交給使用者接手。

投遞狀態至少包含：discovered → matched → prepared → applying → submitted；另有 needs_input、failed、submission_unknown、skipped。只有取得網站成功確認或可核對的回條才標示 submitted。送出後若斷線、結果不明，先查證，不直接重送。以平台職缺 ID／標準化網址去重，並處理同一職缺跨網站重刊。

## 開發順序與驗收

| 階段 | 可用成果 | 驗收方式 |
| --- | --- | --- |
| 0：完整網站共用架構 | 登入、所有模組導覽、共用資料與背景任務狀態、附件保存、Agent 事件入口 | 資料持久保存；使用者隔離；重開頁面可恢復進度；各功能頁面按後續階段完成真實操作 |
| 1：我的經驗與履歷工作室 | 在網站打字／錄音／上傳、整理與編輯經驗、匯出 Markdown、生成並編輯中英文多份履歷、PDF／DOCX 匯出 | 操作全程可由前端完成；逐條追溯經驗；缺失資料標記；中英文日期數字一致；生成和匯出有失敗處理 |
| 2：找職缺與客製履歷 | 前端設定並保存搜尋條件；台灣／國際各至少一個實測搜尋來源；去重、配對原因、職缺詳情與一鍵客製履歷 | 用指定樣本比對原站資料；未知條件如實顯示；每站能力標示；職缺直接連到專用履歷與投遞佇列 |
| 3：投遞中心 | 從網站啟動草稿／批次／規則自動投遞、查看進度、補答、暫停與續跑；台灣／國際各至少一條成功流程 | 真實職缺送出可核對；斷線不重複投遞；文件版本可追溯；不要求使用者執行命令列 |
| 4：面試、面經、Offer 與回覆同步 | 前端管理面試輪次、上傳並整理面經、記錄 offer／最終決定；連接回覆來源後自動更新 | 回覆正確歸屬申請；多輪面試不重複計數；無回覆不視為拒絕；原檔和整理稿可取回；低信心資料待確認 |

架構調整為「網站＋持久化後端＋Agent 執行器」。網站管理使用者、職涯資料、文件與求職進度；Agent 負責搜尋、履歷生成、瀏覽器操作並回報事件。資料庫與附件存放在後端，不能只依賴瀏覽器 localStorage。若瀏覽器自動投遞在使用者電腦執行，以限權憑證連接網站，不上傳整個瀏覽器登入設定。模型呼叫記錄用量與成本，動作設超時與可恢復狀態。

下一個可實作單位：建立完整網站架構並先打通「在網站輸入經驗 → 整理及編輯資料庫 → 生成、編輯、匯出多份履歷」，依序接上網站內的搜尋、客製、投遞、面試與 offer。所有已要求的功能都要有可操作前端，不能將第一版交付範圍縮成投遞紀錄工具。網站開發可用明確標示的測試素材進行；真實求職流程則使用使用者提供的經驗、偏好和已連接服務。
